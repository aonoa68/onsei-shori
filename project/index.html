    テーマA：音声特徴量分析レポート¶

    概要¶

    自分で収録した音声（または適切な許可を得た音声）をMFCC等の特徴量で分析し、その結果と解釈をレポートにまとめる。音声の「中身」を数値・グラフで見ることで、音声処理の基礎に深く触れる課題。

    研究のアイデア例¶

    話者・感情の比較 - 自分の声と別の人の声のMFCCを比較し、話者の違いが特徴量にどう現れるかを分析 - 「嬉しい声」「怒った声」「普通の声」のスペクトル特性の違いを分析 - 「緊張しているとき」と「リラックスしているとき」の声の変化

    言語・音韻の分析 - 日本語の5母音（ア・イ・ウ・エ・オ）のフォルマント分析 - 有声・無声子音の違いをスペクトログラムで視覚化 - 日本語と英語で同じ話者が発話したときの特徴量の違い

    環境・音質の影響 - 静かな部屋・騒がしい場所・電話越しの音声のSNR（信号対雑音比）比較。クリーンな参照信号や雑音区間をどう得るかを示し、推定値と既知の雑音を加えた条件を区別する - 異なるマイク・録音デバイスでの特徴量の変化

    最低要件¶

    • [ ] 自ら収録した音声（または適切にライセンスされた音声データセット）を使用
    • [ ] MFCC（この課題では最低13次元）の計算と可視化（グラフ）。13次元は理論上の固定値ではなく、0次係数を含むかを明記
    • [ ] 比較対象を2種類以上設定
    • [ ] 各特徴量の計算方法と設定（サンプルレート、窓長・ホップ長、メル帯域、対数・DCT、次元数など）の説明
    • [ ] 結果の考察（なぜそのような差が生まれるのかを音声学・信号処理の観点から説明）

    推奨追加要素（加点対象）¶

    • メルスペクトログラムの可視化
    • ピッチ（基本周波数F0）の時系列分析
    • デルタ・デルタデルタMFCCの計算
    • 機械学習を使った話者・感情の識別実験
    • 雑音付加（ホワイトノイズ・バブルノイズ（多数の発話が重なったbabble noise）等）による影響の定量化

    テーマB：Whisperを使った多言語音声認識の精度比較¶

    概要¶

    OpenAI の Whisper（またはその他の音声認識システム）を使って、異なる条件での認識精度を実験的に比較する。データを取り、数値で語る実験的アプローチの課題。

    研究のアイデア例¶

    言語間の比較 - 英語・日本語・スペイン語・アラビア語など複数言語での WER 比較 - 「高資源言語（訓練データが多い）」と「低資源言語（少ない）」の精度差

    方言・アクセントの比較 - 日本語の共通語と、調査対象を具体的に定めた地域の方言。琉球諸語と沖縄で話される日本語の変種を、すべて一つの「沖縄方言」として扱わない - 日本語ネイティブ vs 非ネイティブ（様々な母語話者）

    話者属性の比較 - 年齢・ジェンダー等の比較は、記録方法を明示し、発話内容・録音環境もそろえる。声から本人の属性を推測して割り当てない - ※ 倫理的配慮：参加者から明示的な同意を取ること

    音声品質・環境の比較 - 同じクリーン音声への雑音付加、帯域制限・8 kHzへの再サンプリング、コーデック圧縮など。8 kHzというサンプルレート自体と圧縮方式は別の条件である - 発話速度（ゆっくり vs 普通 vs 速い）の影響

    最低要件¶

    • [ ] Whisper（またはその他の音声認識モデル）の実装と動作確認
    • [ ] 比較条件を最低2種類以上設定し、明確に定義
    • [ ] 正解テキストの用意（WER計算のため）
    • [ ] WER（Word Error Rate）または CER（Character Error Rate）の計算
    • [ ] 結果の考察（訓練データ、モデル、発話内容、録音・評価条件などの仮説と、確認できたことを分ける）
    • [ ] 社会的含意の考察（誰が利益を得て、誰が不利になるか）

    WER・CERの計算¶

    ColabでJiWERを使う例（依存ライブラリの導入は最初に1回）：

    %pip -q install jiwer==4.0.0

    from jiwer import wer, cer

# 英語の単語単位の例：5語のうち1語を置換
reference = "this is the correct sentence"
hypothesis = "this is the correct sent"
print(f"WER: {wer(reference, hypothesis) * 100:.2f}%")  # 20.00%

# 日本語の文字単位の例：4文字のうち1文字を置換
reference_ja = "音声認識"
hypothesis_ja = "音声認知"
print(f"CER: {cer(reference_ja, hypothesis_ja) * 100:.2f}%")  # 25.00%

    参照文が1語以上あるとき、WERの百分率表示は次の通り：

    \[ \mathrm{WER}[\%]=100\frac{S+D+I}{N} \]

    \(S\)は単語の置換数、\(D\)は削除数、\(I\)は挿入数、\(N\)は参照文の単語数。モデル内部のサブワード数とは区別する。CERは文字単位で計算する。

    正解・認識結果には同じ正規化と分かち書きの方針を適用し、その方針を報告する。挿入が多いとWERは100%を超え得る。JiWER 4.0では空の参照文と空の出力を0、空の参照文に対する非空の出力を挿入数として扱う。これは分母0の式とは別の規約なので、無音区間の誤出力は別集計するなど、評価方法を明示する（公式説明）。

    異なる言語のWERを比較する場合は、語の切り方やデータの内容の違いも考慮する。平均値に加えて、話者数・音声量、話者別の分布、モデルの版・設定も記載する。

    テーマC：音声インタフェースのUX提案書¶

    概要¶

    特定のユーザー・状況・目的を設定し、そのための音声インタフェース（音声で操作・入出力するシステム）の設計案を提案する。技術よりも「誰のためのものか」「どう使われるか」に焦点を当てる課題。

    提案の対象例¶

    アクセシビリティ領域 - 視覚障害者向けの音声ナビゲーションシステム - 肢体不自由者向けの音声操作型スマートホームシステム - 読み書き困難（ディスレクシア）の人向け音声入力文書作成ツール

    教育領域 - 小学生向けの音声対話型プログラミング学習ツール - 日本語学習者向けの発音フィードバックシステム - 認知症高齢者向けの日常サポート音声エージェント

    医療・ヘルスケア領域 - 救急現場でのハンズフリー情報入力システム - 精神的サポートのための傾聴型音声インタフェース

    エンターテインメント・日常生活 - 料理中のハンズフリーレシピナビゲーター - 子供の読み聞かせインタラクティブシステム

    提案書の構成（推奨）¶

    1. エグゼクティブサマリー（1ページ）

   - 現状の問題点

3. システム設計
   - 機能一覧
   - 対話フロー（会話の流れ）
   - エラー処理・エッジケース
   - インクルーシブデザインへの配慮

4. プロトタイプ
   - ユーザーフロー図
   - ワイヤーフレームまたはモックアップ
   - （オプション）実装デモ

5. 技術的背景
   - 使用する音声技術の説明
   - 実現可能性の検討

6. 倫理的配慮
   - プライバシー・データ保護
   - バイアスへの対応
   - 誤認識時のリスク管理

7. 考察と今後の展望

   - テーマ選択の理由と研究の問い

2. 音声Deepfakeの技術的背景

    テーマE：自由テーマ¶

    概要¶

    音声処理・音声認識に関連するテーマを自由に設定し、調査・分析・実装・提案のいずれかの形で報告する。

    テーマ設定の条件¶

    1. 音声関連性: 音声処理・音声認識の技術的内容が中心にあること
    2. 独自性: 既存記事の要約にとどまらず、自分の分析・考察・実験があること
    3. 事前承認: テーマを担当者に事前報告し、承認を得ること

    事前確認の方法: - 件名「[音声処理] 自由テーマ事前確認」でメールまたはフォームで連絡 - テーマのタイトルと概要（200字程度）を送付 - 承認または修正提案を1週間以内に返答

    自由テーマのアイデア¶

    技術系 - 音楽情報処理：楽器音の自動分類システムの実装 - 野鳥の鳴き声識別（生物音響学への音声技術の応用） - 音声によるコード（プログラム）入力システムの設計 - 方言音声データセットの構築と分析 - リアルタイム音声翻訳システムの評価

    社会・倫理系 - 吃音者向けの音声インタフェース：課題と改善提案 - 日本語の方言認識の現状と今後の展望 - 音声AIと就労支援：障害を持つ人々へのインパクト - 音声アシスタントにおけるジェンダーバイアスの分析 - 聴覚障害者とリアルタイム字幕：音声認識技術の限界と可能性

    歴史・社会文化系 - 音声記録の保存と復元：文化遺産としての音声アーカイブ - 言語の消滅と音声技術：少数言語の記録・保存への応用 - ポッドキャストの普及と音声認識技術：コンテンツ検索への影響

    提出物と締め切り¶

    提出物¶

    すべてのテーマで共通の提出物。レポート本文は、発表形式A〜Dのどれを選んでも提出します。

    提出物 形式 必須/任意
    レポート本文 PDF または Word（.docx） 必須
    発表スライド PDF または PowerPoint 発表する場合は必須
    ソースコード（該当する場合） .py / .ipynb 等 プログラミングを含む場合は必須
    データ（該当する場合） 音声ファイル、CSV等 実験を含む場合は必須。大容量はURLで可。再配布できないデータは、入手元・識別子・再現手順等を担当者と確認

    レポートの分量目安¶

    テーマ レポート文字数の目安 スライド枚数の目安
    A（分析） 4,000〜6,000字 10〜15枚
    B（実験） 4,000〜6,000字 10〜15枚
    C（提案） 5,000〜8,000字 12〜18枚
    D（調査） 5,000〜8,000字 12〜18枚
    E（自由） テーマによる（担当者と相談） テーマによる

    文字数は厳密なルールではありません。内容の質が最優先です。文字数が多ければよい評価になるわけではありません。

    項目 締め切り
    自由テーマの事前確認（Eのみ） [担当者が連絡]
    最終提出（全テーマ） [担当者が連絡]
    発表当日 第14回授業日

    発表形式の選択肢¶

    すべての形式で評価基準は同一です。どの形式を選ぶかは評価に影響しません。

    形式A：口頭発表（標準）¶

    • スライドを共有しながら口頭で発表（20〜25分）
    • 質疑応答あり（5分）。1件の合計は25〜30分
    • 受講者数・発表形式・必要時間を踏まえた進行と視聴方法は、担当者が事前に案内する

    形式B：事前録画動画の再生¶

    • 発表を事前に録画し、授業中に再生する
    • 発表者本人は授業に参加する必要はない（チャットで質問に回答することを推奨）
    • 録画の長さ：15〜25分
    • 形式：MP4等の一般的な動画形式
    • 提出方法：事前に担当者に共有（ファイル送付またはURLで）

    形式C：スライド+テキスト説明¶

    • スライドを画面共有しながら、テキストチャットで説明を行う
    • 発表者の音声・カメラは不要
    • 時間：20〜25分（テキストのやり取りを含む）

    形式D：書面レポートのみ（発表免除）¶

    • 発表を免除し、詳細なレポートを提出することで代替する
    • レポートは口頭発表があった場合より詳しく書くことを推奨
    • 最終提出日と同じ締め切り

    申請方法¶

    • 希望する形式を発表1週間前までに担当者に連絡してください
    • 当日に形式を変更することも構いません（事前連絡があれば尚よい）
    • 選択理由の説明は不要です

    評価ルーブリック（詳細）¶

    期末プロジェクト・レポートは100点満点で評価し、科目全体の70%を占めます。動画回のCBTと同期回の小課題・演習が残りの30%です。第14回のまとめも同じ基準を用います。

    1. 内容の正確さ（30点）¶

    何を評価するか

    技術的・事実的な内容が正確かどうか。専門用語の使い方が適切かどうか。

    評価段階 点数範囲 基準の詳細
    優秀 27〜30点 技術的内容が正確で、専門用語を適切に使用している。重大な事実誤認がなく、最新の情報を参照している。引用・参考文献が適切に示されている
    良好 21〜26点 内容は概ね正確。軽微な不正確さ（用語の若干の誤用、出典不明の記述等）はあるが、主張の根拠は妥当。引用はあるが一部不完全
    基準達成 15〜20点 基本的な内容は押さえているが、いくつかの誤りや不正確な記述がある。専門用語の使い方に混乱が見られる部分がある
    基準未達 0〜14点 重大な事実誤認が複数ある。または内容が著しく浅く、基本的な概念の理解が確認できない。参考文献がない、または不適切

    良い例

    「MFCCは、メルフィルタで集約した帯域のエネルギー等に対数を取り、DCT（離散コサイン変換）を適用して得る係数である。メル尺度は音の高さの知覚を参照するが、聴覚全体を再現するものではない。本分析では、設定と0次係数の扱いを明記して13次元を用いる。」

    計算の説明はlibrosa公式ドキュメントも参照する。

    避けるべき例

    「MFCCはAIが音声を理解するための数字のリストです。」（技術的内容が不正確・浅い）

    2. 分析・考察の深さ（30点）¶

    何を評価するか

    事実の記述にとどまらず、「なぜ？」「どういう意味があるか？」「どう考えるか？」を示せているか。

    評価段階 点数範囲 基準の詳細
    優秀 27〜30点 技術的事実の背景にある原因・メカニズムを説明している。複数の視点から問題を考察している（技術・社会・倫理等）。自分の見解が根拠とともに示されている。既存研究との対話がある
    良好 21〜26点 考察があり、自分の見解が部分的に示されている。一部に「〜であることがわかる」程度の浅い記述もあるが、全体として考察しようとしている
    基準達成 15〜20点 考察が表面的。「〜という問題がある」と指摘するが、なぜ問題なのか・どう対応すべきかまで踏み込んでいない
    基準未達 0〜14点 考察がほとんどなく、情報の羅列にとどまる。Wikipedia 等をまとめただけのような内容

    良い例

    以下は書き方を示す仮想例で、実測結果ではない：

    「比較した条件AのWERは20%、条件Bは35%で、差は15パーセントポイントだった。同じモデル・設定・正規化を用いたが、語彙と話者も条件間で異なるため、方言だけの効果とは確定できない。学習データの代表性は仮説の一つであり、非公開のWhisper学習データの方言構成をCommon Voiceから逆算することもできない。追加の比較で録音条件と発話内容をそろえ、話者別の分布を確認したい。利用者への影響として、修正回数や必要時間も評価する必要がある。」

    避けるべき例

    「実験の結果、方言の認識精度は標準語より低かった。バイアスの問題があると思う。」

    3. 発表/報告の明確さ（20点）¶

    何を評価するか

    発表またはレポートが、聴衆・読者に伝わるよう整理されているか。

    評価段階 点数範囲 基準の詳細
    優秀 18〜20点 論理的な構成で、主張が明確。「何を伝えたいか」が最初と最後に示されている。図表・グラフが適切に使われ、テキストと連動している。用語は定義されている
    良好 14〜17点 概ね論理的。構成や説明の一部に分かりにくい点があるが、全体として伝わる
    基準達成 10〜13点 内容は伝わるが、構成が不明確。話題が唐突に変わる、主張がどこにあるか不明確な部分がある
    基準未達 0〜9点 構成が不明確で、主張が伝わりにくい。箇条書きの羅列だけで、説明がない等

    注：どの発表形式を選んでも（口頭・録画・テキスト・レポートのみ）、同じ基準で評価します。

    4. 独自性・創造性（20点）¶

    何を評価するか

    単純な情報収集・要約を超えた、自分ならではの貢献があるか。

    評価段階 点数範囲 基準の詳細
    優秀 18〜20点 独自の実験・分析・設計・視点がある。「この人でなければ作れなかった」と言える部分がある。自分の経験・背景・関心と結びついた考察がある
    良好 14〜17点 部分的に独自の視点がある。既存情報を整理するだけでなく、自分の言葉で再解釈している
    基準達成 10〜13点 独自性は限られるが、資料を自分なりに整理しようとした痕跡がある
    基準未達 0〜9点 既存資料のほぼそのままの転用。自分ならではの貢献が見えない

    重要: 他者の文章・コード・成果を自分の成果として提出する剽窃は0点となります。引用・再利用では出典と利用条件を示し、自分の貢献を区別してください。生成AIを補助的に使用することは認めますが、レポートの主要な内容は自分の言葉・分析・実験で構成してください。生成AIを使用した場合はその旨を明記してください。

    総合評価の目安¶

    総合点 目安
    90〜100点 授業の内容を深く理解し、自分の言葉・分析で表現できている。技術と社会の両面への洞察がある
    80〜89点 内容が正確で、考察もある。一部に浅い部分があるが、全体として高い水準
    70〜79点 基本的な内容を押さえ、考察もある。独自性や深さにやや欠ける部分がある
    60〜69点 基準を満たしているが、考察の深さや独自性に課題がある
    59点以下 内容の正確さ・考察の深さ・明確さの複数項目で基準未達

    よくある質問（FAQ）¶

    Q1. テーマはグループで取り組んでもいいですか？¶

    A: 基本的には個人での提出を想定しています。ただし、事前に担当者に相談した上で承認された場合はグループ（最大3名）での取り組みも可能です。グループの場合は、各自の分担と貢献を明記してください。

    Q2. 自由テーマ（E）でAIツールの比較研究をしたいのですが、プログラミングが必要ですか？¶

    A: プログラミングは必須ではありません。既存の音声認識をブラウザや簡易ツールで使って比較する「利用者視点の評価」も考えられます。自由テーマEとして、問いと評価方法を事前に担当者に相談してください。分析の深さは、問いに合う方法、根拠、条件と限界、自分の考察で評価します。プログラミングを行ったことだけで加点されるわけではありません。

    Q3. 参考文献はどの形式で書けばいいですか？¶

    A: 統一された形式であれば、APA・MLA・情報処理学会形式のいずれでも構いません。最低限、著者名・タイトル・出版年・出典（雑誌名またはURL）が含まれていれば可です。

    Q4. 生成AIを使ってレポートを書いてもいいですか？¶

    A: 補助的な使用（調べ物のサポート、アイデアの整理、英語の表現の確認等）は認めます。ただし、レポートの主要な分析・考察・実験は自分で行ってください。生成AIを使用した箇所がある場合は、レポート末尾に「AIツールの使用について」の節を設けて明記することを求めます。生成AIによる文章をそのまま提出することは剽窃として扱います。

    Q5. 発表が怖い・苦手です。どうしたらいいですか？¶

    A: 「書面レポートのみ（形式D）」や「事前録画の再生（形式B）」を選んでいただけます。発表に対する不安は珍しいことではなく、形式の選択で評価が下がることはありません。まず自分が「これならできる」と思える形式を選んでください。発表が不安な場合は事前に小野原に連絡してもらえると、当日に向けて一緒に準備できます。

    Q6. 「独自性」とは具体的に何ですか？論文のような新発見が必要ですか？¶

    A: 学部生に論文レベルの「新発見」は求めていません。「独自性」は次のようなことで示せます：

    • 自分で実験・分析したデータを持っている
    • 既存の情報を自分の言葉で解釈し、「自分はこう思う」という視点がある
    • 自分の経験・背景・関心と結びつけて考えている
    • 「なぜそう思うのか」を自分の言葉で説明できる

    「こんなことを書いても独自性がない」と思う前に、「自分がどう考えるか」を書くことがすでに独自性の出発点です。

    Q7. 音声を録音したいけれど、どんな機材が必要ですか？¶

    A: スマートフォンの標準マイクで十分です。静かな室内で録音すれば、演習で使うには十分な品質が得られます。ノイズが気になる場合は： - できるだけ静かな場所で録音する - スマートフォンを口から15〜20cmほど離す - 収録レベルを確認し、クリッピングを避ける。雑音低減を追加する場合は原音声を残し、処理方法・設定と、音声特徴が変化する可能性を記録する

    librosa.nrというAPIはありません。雑音そのものの影響を調べる実験では、処理によって比較対象まで変わらないよう、原音声と処理後を区別してください。

    高品質なマイクが必要な場合は学科事務室に相談してください（貸出の可否は担当者に確認）。

    Q8. 期末レポートと期末発表の割合はどれくらいですか？¶

    A: 期末プロジェクト全体で科目成績の70%を占め、小課題・演習が30%です。プロジェクト内の評価は、内容の正確さ30点・考察の深さ30点・明確さ20点・独自性20点の同じルーブリックで行います。レポート本文は全形式で必須で、発表する場合はその説明も含めて評価します。この説明書ではレポートと発表を別々の固定比率には分けていません。

    Q9. 倫理審査は必要ですか？¶

    A: 倫理審査の要否は、所属機関の規程と、データ・対象者・実験計画に従って確認します。収録やユーザースタディを始める前に担当教員へ計画を伝え、必要な手続を確認してください。この説明書だけで、一律に不要または必要と判断するものではありません。 - 他人の音声を新たに収録する場合: 目的、利用範囲、共有先などを説明して同意を得ること - 人を対象とした実験（ユーザースタディ等）: 参加者に目的を説明し、任意参加であることを伝え、同意を得ること - 公開データセットを使う場合: ライセンス・利用条件と、再配布できる範囲を確認すること。公開されていることだけで、すべての利用目的が認められるとは限らない

    Q10. 締め切りに間に合わない場合はどうすればいいですか？¶

    A: 事情がある場合は必ず締め切り前に連絡してください。事前連絡がある場合は、状況に応じて期限の調整を検討します。事前連絡なしの遅延は原則として受け付けません。連絡が難しい場合は、メール・フォーム・授業後のチャット等、どの方法でも構いません。

    まとめ¶

    期末プロジェクトは、この授業で学んだことを自分のものにするための最後の機会です。

    評価で重視すること： - 正確な知識に基づいた、自分の言葉での考察 - 技術と社会の両面への視点 - 誠実な取り組み（完璧でなくても、自分が理解したことを誠実に示してください）

    評価しないこと： - 完璧な知識量 - 発表の流暢さ・話し方の上手さ - プログラミングの有無（テーマによる） - 形式の選択（書面のみでも口頭発表と同等に評価します）
